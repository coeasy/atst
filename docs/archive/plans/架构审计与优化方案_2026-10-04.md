# atst 架构审计与优化方案

审计日期：2026-10-04
范围：`coeasy/atst` 当前工作树，协议、Provider 注册与执行、客户端、CLI/HTTP/WS/MCP、流式、数据输出及量化应用边界。本文区分**代码已接通**、**离线验证**和**外部数据服务在线可用**；三者不互相替代。

## 1. 结论摘要

atst 的强项是 TDX 协议实现、统一查询执行、Provider 溯源、严格的契约审计和多种调用入口。当前主调用链在离线代码与自动化测试范围内贯通：

```text
CLI / HTTP / WebSocket JSON-RPC / MCP
                ↓ 参数归一与校验
          Client / AsyncClient
                ↓ QuerySpec
          UnifiedRuntime
                ↓ QueryPlan（单 Provider / Channel）
       DirectProviderExecutor
                ↓ 精确绑定
      Provider adapter / TDX client / 本地 reader
                ↓
     QueryResult + provenance / warnings
```

工作树登记 14 个 Provider、195 项业务 capability；TDX 协议账本登记 85 条命令，协议规格审计覆盖 44 份 YAML（含交易面编解码契约）。这些数字是实现规模，不等于 14 个源都在线，也不等于 195 项能力都经真实市场数据验证。

截至本次更新，前三轮离线审计已完成；本次 Provider 扩展另做一轮“检查—修复—回归”闭环。仓内测试能证明代码链路与契约可用，不证明供应商端点、行情时效、字段完整度或生产部署的可用性。

优先改进建议：先做运行态数据源健康与数据质量可见性，再降低高频批量获取成本，最后扩展有真实样本和一致语义的数据源/量化接口。继续堆 Provider 名称或 capability 数字不会自动提高可用性。

## 2. 项目定位与实现架构

### 2.1 定位

atst 是 Python 数据接入和协议库，覆盖 TDX 二进制协议以及若干 HTTP 数据适配器、本地 vipdoc 文件读取和服务接口。它不是完整量化交易终端，也不自带策略研究工作台、回测撮合器或真实券商交易连接。`atst.trade` 保留协议/帧和模拟器，但真实交易 socket 会 fail-closed。

仓库没有浏览器图形前端。这里的“四面贯通”是 CLI、REST、WebSocket JSON-RPC、MCP 调用面统一进入 Client；下游业务 UI 由集成者构建。

### 2.2 模块分层

| 层 | 关键模块 | 职责及关键约束 |
|---|---|---|
| 协议与传输 | `atst/codec/`, `atst/protocol/`, `atst/transport/`, `atst/client/` | 帧编解码、命令账本、精确/通用/透传解析、主站连接池与同步/异步 TDX 客户端。解析不确定时保留原始信息并给出 caveat，避免伪造语义。 |
| Provider 与数据适配 | `atst/providers/`, `atst/web/`, `atst/reader/` | `PROVIDERS` 是 Provider/Channel/Capability 静态清单；web adapters 承接各外部站点；reader 读取本地二进制行情文件。外部站点格式、限频、可用性不受本项目控制。 |
| 查询契约 | `atst/query.py`, `atst/catalog/`, `atst/domain/`, `atst/typed_query.py` | 归一 capability、标的、周期、Provider、currentness 和参数；执行前 fail-closed 校验；把常用领域数据映射为记录契约。 |
| 执行内核 | `atst/runtime/kernel.py`, `executor.py`, `orchestration.py`, `provenance.py` | Planner 生成单 Provider/Channel 计划，Executor 通过 direct binding 调用；校验执行身份/来源；跨 Provider 仅由显式 `FallbackPolicy` 启动。无结果缓存和隐式跨请求合并。 |
| 流式与结果 | `atst/streaming/`, `stream_contract.py`, `result.py`, `output/`, `sink/` | 显式流状态机、推送/重连/背压能力；结果带 provenance；可选导出 DataFrame、Parquet、CSV、DuckDB。 |
| 服务入口 | `atst/cli/`, `atst/integration/runtime_http.py`, `runtime_ws.py`, `integration/mcp/` | 把 CLI、REST、WebSocket RPC、MCP 输入翻译到 Client，集中错误信封和序列化。 |

### 2.3 一次同步查询的关键步骤

1. 入口解析用户输入并验证字段；CLI 有全量 help 检查，HTTP/WS/MCP 使用边界参数契约。
2. `QuerySpec` 标准化 capability、标的、周期、来源和 currentness。
3. Planner 检查 Provider、Channel、Capability、参数签名及新鲜度要求，提前拒绝不兼容组合。
4. Runtime 生成一个 Provider/Channel 的 `QueryPlan`。TDX 连接池内的主站切换仍在 TDX Provider 内；不会静默切到 Web 数据源。
5. Executor 从 direct bindings 找到唯一实现，获取数据并校验执行身份。
6. 返回 `QueryResult`，携带 Provider、Channel、命令或源信息，以及 warnings/caveats。明确指定 fallback 时，每一次尝试另行写入结果。

异步 Client 镜像同一查询契约；`quotes_batch` 支持保序、逐标的 `ok/missing/failed/not_attempted` 结果。其当前内核是**串行直连**，因此语义易审计，但大量标的吞吐和整体 deadline 能力有限。

### 2.4 调用面现状

| 调用面 | 当前边界 | 贯通判断 |
|---|---|---|
| Python | `Client`/`AsyncClient` 为统一业务入口；`TdxClient`/`AsyncTdxClient` 为协议客户端 | 离线契约和运行时测试通过。 |
| CLI | 41 个顶层/嵌套 help 入口可解析 | help 解析探针通过；真实数据命令仍受 Provider/网络影响。 |
| REST | `/v13/` Client-backed 查询、清单与 health 路由 | HTTP 服务/请求校验在离线集成测试通过；不是面向终端用户的 GUI。 |
| WebSocket | JSON-RPC 查询和每连接订阅生命周期 | 消息、订阅停止和资源生命周期测试通过。 |
| MCP | stdio 工具服务 | schema/handler 和 MCP 集成覆盖通过。 |

### 2.5 腾讯 / 新浪 / 百度估值数据边界

| 来源与入口 | 可取字段 | 时间范围和限制 |
|---|---|---|
| 腾讯 `quotes()` | 当前快照 PE、PB、总市值、流通市值、换手率、量比、涨跌停价 | 仅快照；市值统一为元；PE 源口径不能冒称 TTM；没有该接口的历史市值/股数/股息率序列 |
| 新浪 `fetch_all()` / `all_market()` | 全市场当前摘要中的 PE、PB、总市值、流通市值、换手率 | 当前全市场摘要；新浪单股 `hq_str` 快照本身不含这组财务字段；无历史估值序列 |
| Eastmoney `valuation_history()` | Datacenter 原始历史估值行，PE/PB/PS/PCF 与市值、流通股数相关原始字段可随上游返回 | 日频；当前 atst 方法透传行字段，不应假设每一列始终存在；股息率需确认字段或以现金分红和价格按明确口径计算 |
| 百度 `baidu_valuation_history()`（v1.4.3） | 总市值、PE(TTM/静态)、PB、市现率 | 可选近一年/三年/五年/十年/全部；源值单位原样保留；无已确认的流通股数、流通市值或股息率历史 |

因此实用组合是“腾讯/新浪取行情快照，Eastmoney 取日频流通股/市值和估值原始列，百度扩展长期总市值与 PE/PB/市现率”。
股息率历史目前不能视为三家行情接口的稳定直接字段；若增加派生指标，须固定分红金额口径、除权日、币种和 as-of 规则，避免前视偏差。

## 3. 与 GitHub 类似项目比较

这里按项目公开定位比较，不把不同目标的项目当作同一种库。功能范围会随上游变化，应在选型时复核其 README 和版本。

| 项目 | 主要定位与优势 | 相比 atst 的差异 | atst 的机会 / 短板 |
|---|---|---|---|
| [mootdx](https://github.com/mootdx/mootdx) | 聚焦 TDX 在线行情与本地 Reader，API 直接，使用路径短、用户群和文档成熟。 | 不以统一多 Provider 查询、来源 provenance、多服务面和协议规格审计为核心。 | atst 的协议/架构纵深更强；mootdx 的上手成本更低。atst 应继续简化“取一份行情”的最短路径，并改善发行安装体验。 |
| [easyquotation](https://github.com/shidenggui/easyquotation) | 轻量获取多只股票实时行情，目标直观。 | 能力聚焦行情抓取，非协议/运行时框架。 | atst 可提供更完整来源和错误契约，但 Client/QuerySpec/Provider 概念更多；应保留简洁快捷 API。 |
| [AKShare](https://github.com/akfamily/akshare) | 大量金融数据接口和研究数据类别，便于直接做 pandas 分析。 | 它面向宽覆盖数据接口；atst 侧重 TDX 与可组合的统一执行层。 | atst 有 provenance、错误/能力治理优势；公开 Web 源依赖也面临站点变更风险，量化领域数据宽度仍有差距。 |
| [ZVT](https://github.com/zvtvz/zvt) | 模块化量化研究框架，包含数据、因子、策略/模型和研究 UI 的组合路径。 | 目标更靠近研究/回测应用；atst 明确停留在数据接入基础设施层。 | atst 核心更窄更可复用；若面向实际策略研究用户，需要提供标准数据合同和与常用回测框架的适配例，而非把回测撮合器直接塞进协议核。 |

### atst 的主要优点

- TDX 解析深度、YAML 规格、golden 样本和 codegen/audit 形成相对完整的协议工程闭环。
- 单 Provider 计划与 provenance 让“实际用了哪个源”可追踪；跨源 fallback 显式、可审计。
- 同步/异步、离线 Reader、批量、HTTP/WS/MCP 和输出适配能力集中在一套执行契约中。
- 离线架构守卫覆盖模块可达性、配置可达性、循环终止、资源释放、三方绑定一致性与文档链接。

### atst 的主要缺点

- 功能面和概念较多，195 个 capability 容易造成“目录很大、可用性不直观”；新人要读较多文档才能知道一条能力是否适合生产。
- 项目依赖公共网站和 TDX 服务器；不少 Web endpoint 属于非稳定数据接口，字段与限频可变。
- 零缓存、批量串行是可解释性和数据新鲜度的取舍，但会增加请求数、延时和外站压力。
- 当前不是研究闭环：缺少本项目自己的 point-in-time 数据存储、幸存者偏差控制、回测撮合与策略运行能力。
- PyPI Trusted Publisher、`pypi` Environment 和仓库变量已配置，但 v1.4.3 尚未打 tag；PyPI 发行仍待版本标签触发并通过 Actions。不可把本地 wheel 构建描述成已发布。

## 4. 问题与边界清单

### P0：不能把能力登记误读为线上健康

`Client.capability_statuses()` 给的是仓内 capability 状态，不是每个供应商的实时探活结果。`alive` 不能证明此时端点可达、数据当日更新或返回字段足够。TDX 状态文档记录了扩展市场族连接失效、MAC 候选不可达，以及 F10 下载应答空内容等环境级问题；具体状态会变化，部署前需要重新实测。

TDX 行情字段也存在明确边界：当前 7709 快照结构化面没有可信盘口深度，时间字段不能冒充响应时间。无法验证的字段应为空并带说明，量化策略不能把空值静默填成零。

### P1：数据质量和口径还需跨源标准化

- 建立能力级 source card：最后成功时间、样本数、延迟、缺失率、字段范围异常、分页截断、限流/错误率、复权口径、币种和单位。
- 在结果 metadata 里区分**请求时间**、**源端时间**、**交易所时间**和**数据日期**；缺少源端时间就显式标记未提供。
- 明确各源 OHLCV、成交量单位、成交额币种、交易日/时区、复权类型的规范映射；来源切换时保留 schema/口径差异。
- 加入定期的供应商合同探针与 golden 样本刷新流程；源站 HTML/API 变化时能够迅速定位到 adapter 与字段，而不是在策略端暴露错值。

### P1：多标的快取的吞吐上限

`quotes_batch` 提供了多标的快捷入口和逐标的三态结果，但目前是串行逐标的执行。建议增加有界并发批处理（每 Provider 独立并发/限流预算、总 deadline、部分失败、顺序稳定、取消安全），并测量不同批大小的 P50/P95 延迟、请求数和源站限频。同步/异步应共享同一批量结果模型；不能为了性能绕过 provenance 与单 Provider 约束。

零缓存是目前明确选择，不必默认恢复全局隐式缓存。可以先提供由调用方显式控制的短时行情快照/本地落地层，定义 TTL、freshness、键包含 Provider 与口径、缓存来源 provenance 和失效规则；策略回测等历史路径使用 Parquet/DuckDB 分区，而不是读实时缓存。

### P1：实际量化研究场景的接口深度

按真实研究需求补接口，而非追求 API 数量：

1. **复权历史与事件**：日/分钟 K 线、复权因子、除权除息事件同一证券/时间轴对齐，提供前复权/后复权/不复权标识和 as-of 口径。
2. **point-in-time 基本面**：报告期、公告时间、修订时间分开；支持“当时已知数据”查询以降低前视偏差。
3. **可回放股票池**：交易日历、历史指数/行业成分、上市/退市与 ST 历史快照，显式支持 survivorship-free universe。
4. **分钟/逐笔**：交易所时间、序号、集合竞价阶段、成交量单位和缺口状态；真实覆盖不全时按市场和来源暴露能力状态。
5. **期货/期权**：合约到期日、主力换月规则、连续合约构造口径、保证金/乘数、交易日历、期权合约链和 Greeks 的来源/算法标记。
6. **跨资产宏观**：利率、汇率、宏观指标增加发布日、频率、修订/版本和币种元信息，避免把后来修订的数据带入历史模拟。
7. **回测适配，而非回测内核**：给 Backtrader/vectorbt/Zipline 等常见消费侧写适配与防前视样例；交易执行维持独立项目或 adapter 边界。

### P2：更多数据源怎么加

建议按“语义缺口和可靠性”排序，先为同一能力引入不同实现，再扩展全新领域：

- 优先验证独立历史日线/复权/日历来源，以及 token 型、配额透明的研究数据源；把免费源和需要凭据的源分别列明。
- 评估 [Baostock](https://github.com/baostock/baostock)、[Tushare](https://github.com/waditu/tushare) 等作为可选 Provider adapter；确认数据许可、注册/token、速率配额、复权和历史完整度后，再决定生产接入。
- 可将 AKShare 当作可选适配依赖或参考数据源入口，不应把它的接口名直接复制成 atst 公共契约；锁版本、离线 fixtures、对关键字段做契约验证。
- 仅当合法授权且用户配置凭据时接入券商/商业行情；认证、密钥托管、限额和市场数据许可需要独立评审。
- 每个新源至少交付：Provider/Channel/Capability 注册、adapter、参数校验、canonical 或 provider-specific schema、单位/时区/复权说明、freshness/provenance、错误/限流语义、脱敏、离线 fixture、同步/异步边界说明及文档。一次实现应穿过 Python、CLI/REST/WS/MCP 的受支持入口，或明确标注为仅库面能力。

不要按“有多少 Provider”做目标。建议用“每个关键量化场景的独立可用源数、当日成功率、P95 延迟、字段完整度、历史覆盖率、单位测试与线上探针一致率”衡量改善。

### P2：部署、发布与扩展性

- 把 REST/WS 服务放在受信任网段或反向代理之后，明确鉴权、TLS、速率限制、来源白名单和敏感信息脱敏的责任归属；不要因本地服务能启动就视作互联网可安全暴露。
- 提供最小容器部署/健康检查/Prometheus 指标/优雅停机示例，并把健康端点区分为“进程就绪”“本地依赖可用”“远程 Provider 探测”。
- 明确 PyPI 与 GitHub Release 分发计划、安装验证矩阵、Python/平台兼容矩阵，降低使用者必须从源码安装的摩擦。
- Provider adapter 数量增多后，形成插件开发模板与 conformance kit，让注册表、Schema、Bindings、能力目录和多调用面合同自动生成或做一致性检查，避免同一事实多处维护。

### 验证限制

这些门禁证明代码层面预期路径可达、契约一致、错误/资源边界可控，不证明当前所有 Provider 的真实网络请求成功。本轮未以真实行情接口作为通过条件，也未连接真实券商；线上覆盖与数据正确性需要单独运行受控的 live smoke，并保存数据日期、市场、源端与字段校验报告。

## 6. 建议实施顺序与验收标准

| 优先级 | 交付 | 验收标准 |
|---|---|---|
| P0 | 当前 capability/Provider 在线健康与字段质量仪表；区分实现状态和探活状态 | 每项能力能看到最近成功、错误类别、端到端耗时和字段 caveat；默认不触发大量外部请求。 |
| P0 | 为关键端点建立可复现 live smoke 和契约漂移告警 | 在不依赖单次公共站点波动的离线门禁外，定时运行、保留报告；未验证能力不标成生产可用。 |
| P1 | `quotes_batch` 有界并发、deadline/取消与每源限流 | 保序与三态不变；部分失败清楚呈现；并发测试和延迟基线通过；不会跨 Provider 隐式切源。 |
| P1 | 统一时区、成交量/金额单位、调整类型、as-of 时间元数据 | 同一标的和周期的不同 Provider 有映射/差异表；未提供字段保留 null 和 caveat。 |
| P1 | 历史股票池、point-in-time 基本面与复权事件接口设计 | 提供防前视数据样例、历史回放 fixture 和 schema 文档；公开数据日期/修订信息。 |
| P2 | 新 Provider 插件模板及 1–2 个高价值源试点 | 真实许可/配额确认；接入最小完整链；测试覆盖；用可靠性和成本数据决定是否继续。 |
| P2 | 回测框架消费侧适配与部署安全范例 | 示例可离线运行，数据边界清楚；服务部署责任和鉴权/TLS 做法明确。 |
