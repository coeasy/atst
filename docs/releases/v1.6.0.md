## 一句话

tdx 协议族那个「请求体把 market 写到 code 后面」的老毛病第三次发作，这次落在当日分时
（`0x0537`）与当日逐笔（`0x0FC5`）上；两条命令的解析器也一并按真机布局重写（leb128 差分，
一个「基准+增量」、一个「逐笔累加」，模型相反），双市场 golden 锁定后升 L1。

## Fixed

### 请求体字节序：`0x0537` / `0x0FC5`

TDX 标准族命令的请求体一律是 `<H market><6s code>…`（**市场在前**）。这两条发的是
`<6s code><H market>…`。服务端按 market-first 解读时，请求体的前 2 字节被当成代码字符读成
ASCII 码点而越域：

| 市场 | 代码前两字节 | 服务端读到 | 结果 |
| --- | --- | --- | --- |
| 沪市 | `'6''6'` | 码点越域 | **4 字节空桩**（看起来"命令没数据"） |
| 深市 | `'0''0'` | 恰好落在容差内 | 碰巧有响应（残缺代码被宽容） |

所以这个 bug 的症状是"沪市全空、深市像好的"——最容易被读成"上证主站没数据"而不是"我们发错了"。
同一份病此前已在 `0x0010`（财务）与 `0x000F`（除权除息）上发作过一次（v1.5.4 之后修正）。
现在两条都发 12 字节 market-first 请求体，6/8 主站 × 双市场均回满日数据（另 2 台 TCP 不可达）。

### 响应解析：leb128 差分，但两个模型相反

旧解析按定长记录猜。两条命令实际都是 **6 位前缀有符号 leb128**（首字节 `[7]=续位 [6]=符号
[5..0]=数据`，续字节 7 位，位移 6/13/20…），但价格的组合方式相反：

| 命令 | 记录布局 | 价格模型 | 标度 |
| --- | --- | --- | --- |
| `0x0537` 分时 | `[leb128 price_delta][leb128 avg_delta][leb128 vol]` × n | **基准 + 增量**：记录 0 绝对，其余相对记录 0 | 价格 `/100`，均价 `/10000`，量单位手 |
| `0x0FC5` 逐笔 | `[<H 分钟>][leb128 price_delta][leb128 vol][leb128 笔数][leb128 买卖][leb128 保留]` × n | **逐笔累加**：`Σ price_delta` | 价格 `/100` |

抄错一条，整条记录流从第一条起就错位。交叉验证用的是本仓库自己的 L1 证据——同日 `0x052D`
一分钟 K 线：

- `0x0537`：价格 **240/240**、成交量 **240/240** 与 K 线逐条相等；均价 239/240（记录 0 是绝对值）；
  缓冲区按字节精确耗尽（沪市 1196B、深市 1223B，`leftover == 0`）。
- `0x0FC5`：逐笔成交量按分钟汇总 **237/240** 完全相符，3 条例外是集合竞价折叠
  （09:25 + 09:30 = 09:31 桶，`268100 + 2763000 = 3031100` 双市场各自可验）；
  连续竞价时段 **100%** 的逐笔价格落在其所属 K 线 bar 的最高/最低区间内；
  最后一笔价格与实时 `0x0530` 快照一致（9.66 / 11.41）。

### 一处对 pytdx 的误判

pytdx 的 `GetMinuteTimeData` 把 `0x0537` 的价格当累加模型解。做了对照实验：本仓库的
「基准 + 增量」对 K 线收盘价 **239/240** 相符，累加模型只有 **2/240**。本仓库的模型是对的，
已写进解析器 docstring 与 PROTOCOL_SPEC，避免下游照抄。

### 分钟标签差一分钟（不是 bug，但会误判）

K 线 bar 的标签是**区间末分钟**（`09:31` 这根覆盖 `09:30:00–09:30:59`），`0x0FC5` 逐笔的
标签是该笔的**真实时钟分钟**。两者天然差一分钟：开盘集合竞价（09:25）折进 09:31 那根，
收盘集合竞价折进 15:00 那根，`11:30:00` 边界那一笔折进 11:30。对账时必须先对齐这个偏移，
否则会得到"每个桶都差一点"的假结论。

## Added

- **`minute` / `trades` 的 tdx 源从「发包前即拦」变为 L1 可用**：`0x0537` / `0x0FC5` 双双升
  `tier=L1, verified=True`；`atst/client/core.py` 的 `_UNVERIFIED_STRUCTURED_BLOCK` 清空
  （常量与分支保留，只留空集合）；两份 PROTOCOL_SPEC 改 `status: verified` 并补 `measured:`
  证据块；重新采集双市场 golden 样本。
- **`golden_audit.scan_corpus` 排除病理存档**：新增 `ARCHIVE_DIR_NAMES`，跳过
  `tests/golden/quotation/_archive_wrong_request/`（22 个目录全是写反请求体采的空壳）。
  此前这些样本进分母，把"采过了"误报成覆盖率。
- **MCP 工具描述同步**：`get_minute_today` / `get_trades` 从 "unavailable because its
  request/parser is still inferred … (NotImplementedFeature)" 改为 L1 可用口径。

## 兼容性

- 公开 API 无签名变更：`Client.minute` / `Client.trades` / `TdxClient.minute_today` /
  `TdxClient.trade_today` 的形参一字未动。
- 行为变更（唯一的破坏面）：`provider="tdx"` 的 `minute` / `trades` 从抛
  `NotImplementedFeature` 改为正常返回。此前依赖"抛这个异常"来做能力探测的代码需要改判据——
  用 `Client.capability_statuses()` 或 `TdxClient` 侧 `CommandOffline` 判别。
- 死名字表从 8 个减到 6 个（`minute` / `trades` 除名），其余六个不变。

## 验证

- 完整套件（本机，`python -m pytest tests`）与 pristine `HEAD` 逐条对比。
- 双市场实采：`6/8` 主站应答，`2` 台 TCP 不可达；沪市 `600000`、深市 `000001` 各回满日 240 条。
- 缓冲区精确耗尽：`0x0537` 1196B / 1223B，`leftover == 0`；`0x0FC5` 4 份存量样本 + 实时载荷同样耗尽。
