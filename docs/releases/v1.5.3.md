## 一句话

把"日线"在六张面上的形状收成一种（`YYYY-MM-DD 15:00`），并给两处**真有歧义的空结果**
补上告警：粗周期（周/月/季/年）窗口落在周期内部时的空，以及指数分钟线首根与服务端
名义口径对不上时的量。

## Added

### 日线 `datetime` 跨源统一：`YYYY-MM-DD 15:00`

日线及以上周期没有时间分量，约定 `Bar.datetime` 指向**该周期的结束时刻**。tdx 协议解析器
本来就这么落值（`_std7709_bars._read_datetime`），但五家 Web 源与本地 vipdoc 日线读取器
历史上各吐各的形状：

| 落点 | 旧形状 |
| --- | --- |
| 腾讯 fqkline / mkline（`atst/web/_paginate.py`） | `"2026-08-28"` |
| 新浪历史 K 线 | `"2026-08-28"` |
| 东财 push2his（股票日线） | `"2026-08-28"` |
| 东财衍生（期货/债券） | `"2021-08-17"` |
| 百度 K 线 | `"20260828"`（紧凑） |
| 本地 vipdoc `DayBarReader` | `"2026-08-28"` |

同一份"日线"在跨源比较 / 排序 / 去重时都得先猜形状。现在统一经
`atst.domain.calendar.day_like_datetime` 归一：

```python
from atst.domain.calendar import day_like_datetime

day_like_datetime("20260828")          # '2026-08-28 15:00'
day_like_datetime("2026-08-28")        # '2026-08-28 15:00'
day_like_datetime("2026-09-01 10:05")  # '2026-09-01 10:05'（已带时刻，原样放过）
```

归一用**形状判据**而不是 `period` 参数：这样腾讯 fqkline 那条同名路径上的日线与分钟线
各得其形状，不必再加一个参数往下穿。东财**板块**日线本来就带时刻（上游下发的
`"2026-08-31 15:00"`），形状判据天然放过。

**已知瑕疵（有意保留）**：港股 / 美股日线也会补成 15:00，而港股实际收盘 16:00。
这里统一的是**形状**（"日线无时间分量，指向周期结束"），不是逐市场的真实收盘时刻——
不引入"市场 → 收盘时刻"映射，那会让同一个字段同时承担两种语义。

内核所有消费点（`atst/sink/local_day.py`、`atst/runtime/executor.py` 的区间裁剪、
`atst/domain/adjust.py`）本来就先切 `[:10]` 再比日期，因此这是外部形状的收敛，
内核逻辑一行未动。

### 新诊断 `bars_range_interior_empty`

`bars` 的日期区间落在取回 K 线**跨度的内部**（两侧都有 bar）却一根都没命中，且周期是
粗周期（`week` / `month` / `season` / `year`）时告警。这些周期的 bar 以「周期末的那个
交易日」为 `datetime`（未走完的周期取最新交易日），窗口落在周期内部时按日期裁剪必然为空。

实测形状：`year` 周期取 `2026-09` 区间回空——2026 年的 bar 挂着最新交易日，2025 年及更早
的 bar 都在区间起点之前。这既不是"这些日期没有行情"（`day` 周期取休市日），也不是
"页没取到区间之前"（`bars_range_uncovered`）。三条判据的分工：

| 诊断 | 触发条件 |
| --- | --- |
| `bars_range_uncovered` | 取回的页**没触及**区间起点之前（count 不够，区间只是一段） |
| `bars_range_interior_empty` | 页已触及之前，区间被夹在两段 bar 之间却命中不到，且周期为粗周期 |
| （无告警） | 区间落在页内但没有行情（休市日 / 未来区间 / 完整覆盖区间） |

### 新诊断 `index_minute_volume_inconsistent`

0x052D 指数**分钟线**的 `volume` 与"名义口径"（= 成交额 / 100）差了一个数量级以上时告警。
名义口径只在**完整交易日**成立：2026-10 实测 10 周期 × 3 标的矩阵里唯一偏离的形状是指数
60min 的当日首根，服务端下发的 `volume` 比名义口径低约 97 倍，而同一时段由 15min / 30min
聚合出的 `amount` 完全吻合。原始字节手工核对确认记录边界精确耗尽（解析器无错位），
即**服务端自己下发的不一致值**——不是解码错位，也不是口径理解错。

判据是单侧的（只在 volume 明显偏小时发），与 `index_minute_volume_nominal` 并存：后者说明
"这一族字段本来就不是真实成交股数"，前者说明"这一根连名义口径都对不上"。

## Fixed

- `index_minute_volume_nominal` 的文案原写「恒等于成交额/100」——该等式只在完整交易日成立，
  首根对不上时会被读成"解码坏了"。改为「按名义口径等于」。
