# ADR-001: 零硬依赖架构

**状态**: Accepted  
**日期**: 2026-08-31  
**决策者**: 核心维护者

## 背景

tstdx 需要支持多种使用场景（量化研究、交易策略、数据分析），不同用户对依赖有不同需求。全功能依赖包会阻碍轻量化部署场景。

## 决策

采用**零硬依赖 + Optional Extras** 架构：

- 核心运行时无第三方硬依赖
- 所有功能模块可通过 pip extras 按需安装
- 使用条件导入（`try: import X except ImportError`）优雅降级

## 影响

- ✅ 安装体积小（基础安装 <500KB）
- ✅ 可嵌入资源受限环境
- ✅ 按需安装，避免依赖冲突
- ❌ 代码复杂度略增（条件导入模式）

## 替代方案

- 全功能单包（已拒绝：阻碍轻量部署）
- 微服务拆分（已拒绝：过度工程化）

# ADR-002: 同步/异步双 API 镜像

**状态**: Accepted  
**日期**: 2026-08-31  
**决策者**: 核心维护者

## 背景

用户场景分为同步（脚本、CLI）和异步（asyncio、Web 服务）。两种模式需要统一的 API 设计。

## 决策

- `TdxClient`（同步）+ `AsyncTdxClient`（异步）方法签名完全镜像
- 同步客户端内部使用连接池 + 线程安全
- 异步客户端使用 asyncio + 连接池

## 影响

- ✅ 用户可在两种模式间无缝切换
- ✅ 测试可以用 fake pool 注入
- ✅ 共享协议解析层

# ADR-003: L1/L2/L3 三级解析分派

**状态**: Accepted  
**日期**: 2026-08-31  
**决策者**: 核心维护者

## 背景

TDX 协议命令数量多且部分未文档化。需要一套机制既能解析已知命令，又能处理未知/漂移命令。

## 决策

- **L1**：精确匹配已知命令的解析器（60+ parsers）
- **L2**：基于启发式规则的通用解析器（generic.py）
- **L3**：原始字节透传（仅返回 bytes，不做解析）

分派器（registry.dispatch）按 L1→L2→L3 顺序尝试。

## 影响

- ✅ 未知命令不会崩溃
- ✅ 新命令可通过 L3 先获取原始数据
- ✅ ProtocolSniffer 可从 L3 数据生成 spec 草稿

# ADR-004: HTTP Web 源降级策略

**状态**: Accepted  
**日期**: 2026-08-31  
**决策者**: 核心维护者

## 背景

TDX 主站可能不可达（网络问题、IP 封禁、服务端宕机）。需要多源降级保证可用性。

## 决策

- 5 级降级链：TDX → HTTP Web → 本地 vipdoc → 缓存 → 合成数据
- DataSourceRouter 统一管理降级策略
- HTTP Web 源：14 个源模块 / 45 个 Source 类（上游覆盖新浪/腾讯/东财/集思录/中行/同花顺问财）
- 每个 Adapter 有独立反爬检测和下线检测

## 影响

- ✅ 可用性大幅提升
- ✅ 离线也能使用本地数据
- ❌ 字段口径需要归一化（normalize.py）

# ADR-005: PROTOCOL_SPEC YAML 规范

**状态**: Accepted  
**日期**: 2026-08-31  
**决策者**: 核心维护者

## 背景

协议命令解析器需要文档化，且需要支持 codegen 和契约测试。

## 决策

- 使用 YAML 描述每个命令的请求/响应字段布局
- 每个 spec 包含：spec_id, name, family, request, response, notes
- codegen 工具可从 spec 生成解析器骨架
- spec_audit 工具验证 spec ↔ 实现的一致性

## 影响

- ✅ 协议变更可追溯
- ✅ 新命令可通过 spec 快速实现
- ✅ 支持 spec 驱动测试
