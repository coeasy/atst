# 0x000F / 0x0010 / 0x0537 错请求样本存档

**这些样本不是契约，是病史。**

2026-10-21 定位并修复了一个静默错位缺陷：`finance`(0x0010) 与
`capital_changes`(0x000F) 的请求体发的是 `<6s code><H market>`（代码在前），
而服务端按 `market@2 / code@3:9` 解读，于是记录头整体错位——`market` 读到
ASCII `'0'`(48)、`code` 只剩半个代码，且前 2 字节被当成「请求条数」读成
十进制 12336，服务器于是回一大块**服务端缓冲残留**（内容每次抓包都不同）。

本目录下的 8 份样本（2026-08-31 / 09-02 采集）全部是用那个错请求体采的：

* `0x0010_*`：响应 14302 字节 = 100 条记录，只有第 1 条是本人，其余 99 条是
  缓冲残留。旧「四份样本均回 14302 字节」的结论正来源于此。
* `0x000f_capital_changes_600000/20260831-125354`：2252 字节，按修正后的两级
  结构（`<H blocks><块头 9B><num × 29B>`）解出 0 行。
* `0x000f_*` 其余两份：解出的「行」是缓冲残留被当成块/记录读的产物，字段值
  落在域外——F-37 当年量到的越域行全部来自这里。

修正后的请求体是 9 字节 `<H 1><B market><6s code>`（前 2 字节 = 请求条数）。
用新请求体重采的样本在上一级目录的 `20261021-*` 时间戳目录里，两级结构下
缓冲区按字节精确耗尽（0x000F 浦发 88 条 / 平安 81 条），0x0010 一条 143B
干净记录。

## 0x0537（minute_today）批次：同一个病，第二次发作

2026-10-21 深夜定位：`minute_today`(0x0537) 的请求体同样发成了
`<6s code><H market><I 0>`（代码在前）。服务端按市场在前解读时：

* 上证（market=1）：前 2 字节读成 ASCII `'6'`+`'6'` = 0x3636，市场号越域 →
  **直接回 4 字节空桩**（`num=0`）。这也是 golden_audit 长期标记
  `0x537 4B<12B x3`「疑似过短」的来源。
* 深市（market=0）：前 2 字节读成 `'0'`+`'0'` = 0x3030，`code` 段退化成
  `"0001\x00\x00"`，靠服务端对残缺代码的宽容才碰巧拿到 120 条数据——
  能解出东西纯属侥幸，不能当契约。

本目录下的 `0x0537_*` 共 20 份样本（2026-08-31 / 09-02 采集，含 16 份
`_syn_` 批量）全部用错请求体采得：19 份是 4 字节空桩，1 份（深市
`000001`）是上面那条侥幸数据。

修正后的请求体是 12 字节 `<H market><6s code><I 0>`（市场在前）。用新请求体
重采的样本在上一级目录 `0x0537_minute_today_{600000,000001}/20261022-000324/`：
两个市场各 240 条完整交易日，缓冲区按字节精确耗尽，且与同日 L1 已验证的
0x052D 一分钟 K 线**价格 240/240、成交量 240/240** 全对齐。

**为什么不直接删**：`tests/client/test_decode_caveat_wiring.py` 的
`TestDomainCaveatReachesTheWire` 需要一份「真实错位页」当负控——证明块/记录头
与请求不符时告警真的会上 wire。这些样本是真实的错请求响应，正好承担这个角色。
它们位于 golden 根下第 4 层，`tests/unit/test_golden.py` 的回放 glob
（`*/*/*/meta.json`，3 层）不会捡到它们。

**什么时候可以删**：0x000F/0x0010/0x0537 的字段口径由本仓 golden 正式锁定
（账本 `verified=True`、F-37 收口）之后，这份负控改用新采样本的变异副本即可。
